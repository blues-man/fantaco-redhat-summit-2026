## 1. What this feature is

Step 6 of the RHOAI MaaS guide: **per-request** token / user / subscription
detail, on top of the aggregate Usage tab that already exists. It gives two
Perses dashboards, generated by the MaaS controller, not by us:

| Dashboard | Groups by | Note |
| --- | --- | --- |
| `dashboard-4-maas-usage-logs-admin` | `user_id` | always worked |
| `dashboard-5-maas-usage-logs` | **`key_name`** | the one the stock product breaks |

The guide deploys MinIO and calls it non-production. We use the ODF/NooBaa
ObjectBucketClaim pattern this repo already has (8 files reference
`ObjectBucketClaim`), so there is still no AWS dependency.

## 2. Gap analysis against this repo, as of this commit

I grepped the tree. Nothing models this yet:

`components/tracing/` already models the RHOAI MLflow path correctly — that

different namespace. Do not merge them into `components/tracing`.

## 3. What to add

Suggest a new `components/maas-usage-logs/` rather than extending
`components/observability`, because the LokiStack lives in
`redhat-ods-monitoring` (not `openshift-logging`) and its lifecycle is tied to
the MaaS `Config`, not to the logging stack.

**a. ObjectBucketClaim** — `maas-usage-logs`, storage class
`openshift-storage.noobaa.io`, namespace `redhat-ods-monitoring`. Then build
the `maas-usage-logs-s3` secret from what NooBaa writes on bind. Reuse whatever
`components/observability/templates/loki-s3-secret-job.yaml` does; the contract
is identical.

**b. LokiStack `usage`** in `redhat-ods-monitoring`. Name **must** stay `usage`
— the RHOAI operator looks for exactly that. Copy
`operator-patches/maas-usage-logs-lokistack.yaml`, but **use
`{{ .Values.lokiStackSize }}` (`1x.extra-small`), not the scripts' `1x.demo`.**
The scripts ship `1x.demo`, which runs one ingester at replication factor 1 and
permanently reports `Warning=True`: *"ingester replicas (1) are less than or
equal to the replication factor (1). Which causes log ingestion to stop when
ingester pods get restarted."* `Ready` is still True and ingestion works — I
measured it — but usage records are lost across an ingester restart. This repo
already defaults to `1x.extra-small`, so GitOps gets this right for free. Don't
copy the `1x.demo` regression in.

Keep `limits.global.otlp.streamLabels` exactly as in the manifest
(`service.name`, `subscription`, `model`, `response_type`,
`kubernetes_namespace_name`). **The dashboards query on those labels**; drop one
and panels silently go empty.

**c. The switch**: `configs.maas.opendatahub.io/default`, `spec.usageLogging:
true`. This is a **patch to an operator-owned singleton**, not a resource we
create — see §4.

**d. The key-attribution fix** — see §5. This is the part that needs real
thought.

## 4. The ownership problem, which is the whole difficulty here

Three objects in this feature are **generated and owned by `maas-controller`**:

- `EnvoyFilter/maas-model-access-logs` in `openshift-ingress`
  (`ownerReferences` → `maas.opendatahub.io/v1alpha1 Config/default`,
  `app.kubernetes.io/managed-by=maas-controller`)
- `AuthPolicy/maas-gateway-auth` in `openshift-ingress`
  (`managed-by=maas-controller`)
- both PersesDashboards

Argo cannot own these. Attempting to manage them declaratively will either
fight the controller or, worse, look fine until the controller next
reconciles. You already hit this shape in `5914c92` *"Stop Argo reverting the
MLflow experiment id"*.

Use the post-sync Job pattern this repo already uses in twelve places
(`experiment-job.yaml`, `dashboard-flags-job.yaml`, `authorino-cert-job.yaml`,
`dsci-monitoring-job.yaml`, …): a hook Job that patches, is idempotent, and can
re-run. `fix-maas-key-attribution.sh` is already written to be exactly that —
idempotent, with a `--check` mode — so the Job can more or less shell it.

**Ordering matters:** the EnvoyFilter does not exist until `usageLogging: true`
has been reconciled. The patch Job must run *after* that, and must tolerate the
object not being there yet. The script sleeps 30s then retries `oc replace` up
to 3 times on conflict; a Job should do the same or poll.

## 5. The bug the fix works around (RHOAI defect, not ours)

Stock, `key_name` and `key_id` log as `-` forever, so
`dashboard-5-maas-usage-logs` collapses every request into a single `-` series.
The admin dashboard groups by `user_id` and looks perfect, **so this is
invisible unless you open the non-admin view.** That is why it survived several
events unnoticed.

Cause: the generated EnvoyFilter reads
`%FILTER_STATE(wasm.kuadrant.auth.identity.keyId:PLAIN)%`. That resolves to
nothing. I probed it properly before concluding:

- emitting the **whole** `wasm.kuadrant.auth.identity` blob → `-`
- all six `DYNAMIC_METADATA` spellings → `-`
  (`envoy.filters.http.ext_authz`, `…:identity`, `kuadrant.auth.identity`,
  `…:keyName`, `wasm.kuadrant.auth.identity`, `…:keyName`)

The data exists: POST a seat key to
`https://maas-api.redhat-ai-gateway-infra.svc:8443/internal/v1/api-keys/validate`
and it returns `keyId`, `keyName`, `username`, `subscription`. And `user_id`
populates fine — because it travels a **different route**: AuthPolicy
`response.success.headers` → `X-MaaS-*` request header →
the EnvoyFilter's `header_to_metadata` filter → access-log CEL.

So the fix sends the key fields down that same proven path:

1. AuthPolicy `spec.defaults.rules.response.success.headers`: add
   `X-MaaS-Key-Name` and `X-MaaS-Key-Id`, `plain.selector`
   `auth.metadata.apiKeyValidation.keyName` / `.keyId`, with the same
   `when` predicate the other headers use
   (`request.headers.authorization.matches("^Bearer sk-oai-.*")`).
2. EnvoyFilter: add `header_to_metadata` `request_rules` for those two headers
   (**two** filter patches carry that config — patch both), and rewrite the
   `key_name` / `key_id` access-log attributes to the same CEL shape `user_id`
   uses.

Measured result: three seats reported distinct `key_name` / `key_id`, the
`key_id` matched what the validate endpoint returned for that seat, and the
dashboard's own LogQL returned four series instead of one. It survived 10
minutes without `maas-controller` reverting it — but see §4; an operator
upgrade or a `usageLogging` toggle regenerates the objects and the Job must
re-run.

**This belongs upstream in RHOAI.** We are patching around a product defect. If
it gets fixed, this component should drop the Job, not keep both.

## 6. Do not bother with `organization_id`

The EnvoyFilter also emits `organization_id` from filter state. The AuthPolicy
exports **no `organizationId` property at all** — I listed them:
`groups, groups_str, keyId, keyName, selected_subscription,
selected_subscription_key, subscription_error, subscription_error_message,
subscription_info, userid`. There is no source. It will read `-` whatever you
do, and no dashboard references it. Leave it.

## 7. Risk to flag in the Application description

Enabling this installs an EnvoyFilter on **`openshift-ingress`** — the gateway
every inference request and every audience route goes through. It is the log
source, so it cannot be skipped. The script applies it last and immediately
re-tests inference; a GitOps sync has no equivalent safety net, which is an
argument for a post-sync verification Job that fails loudly.

I measured no inference disruption on `rosa-wv5l4` — 200s from several seats
before and after, including a full agent turn through MCP — but that is one
cluster, once.

## 9. How to verify, next cluster

The cluster is gone, so this is the procedure rather than a result:

```bash
# 1. components exist
oc get obc maas-usage-logs -n redhat-ods-monitoring
oc get lokistack usage -n redhat-ods-monitoring \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status} {end}'   # expect Ready=True, Warning=False
oc get configs.maas.opendatahub.io default -o jsonpath='{.spec.usageLogging}'

# 2. the fix is applied (NOT just present — check the CEL, not the object)
oc get envoyfilter maas-model-access-logs -n openshift-ingress -o json | grep -c x-maas-key-name   # expect >0

# 3. drive traffic from two different seats, then query Loki through the gateway
#    tenant is `application`; needs Authorization + X-MLflow-style workspace is NOT used here
oc port-forward -n redhat-ods-monitoring svc/usage-gateway-http 18080:8080
curl -sk -H "Authorization: Bearer $(oc whoami -t)" --get \
  --data-urlencode 'query=sum by (key_name) (sum_over_time({service_name="models-as-a-service", response_type="hit"} | unwrap tokens_total [1h]))' \
  https://localhost:18080/api/logs/v1/application/loki/api/v1/query
# PASS = one series per seat with a real key_name. FAIL = a single "-" series.
```

Step 3 is the only test that actually proves the feature. Steps 1 and 2 pass
happily while the dashboard is useless — that is exactly how this shipped
broken.

## 10. Open questions for you

1. New `components/maas-usage-logs/` versus extending
   `components/observability/`? I lean new, for the lifecycle reason in §3, but
   you own the chart layout.
2. Should the key-attribution Job live in the new component or alongside the
   other MaaS patches in `components/maas/`? It patches an object the MaaS
   controller owns, so `components/maas/` is arguably its home.
3. Is `usageLogging` something every deployment wants on, or a values flag?
   It adds a LokiStack plus an EnvoyFilter on the shared ingress gateway. For
   scale: at `1x.demo` I counted **11 pods** on `rosa-wv5l4` (compactor,
   distributor, gateway x2, index-gateway, ingester, logs-collector x2,
   tenancy-proxy, querier, query-frontend). `1x.extra-small` is larger — I did
   not measure it, so size the node budget before enabling it by default. The scripts make it opt-in by being a separate
   script; GitOps has no equivalent unless you gate it.
